# AGENT 执行方案：电气夹层抽拉柜可视化动作与全场景配色

> 更新：2026-09-06。项目：`/home/live/work01`。
> **最新用户目标：系统仅用于观看，不与真实硬件协同。画面无需“演示模式”等标注。**
> 本文是独立的新执行方案，原“具体执行方案”和“后续实现与验收执行方案”保留不变。本方案按用户最新的观看用途，以可交互作业动画实现，优先完成流畅、完整、可重复的开合过程。
> **无人值守：无需向用户提问或等待确认，Agent 在本任务范围内自行决策、实现、验证。**

## 1. 最终交付目标

用户通过现有 Web 界面点击打开/关闭，看到：

1. 机器人到达柜前，双臂平滑到工作位姿。
2. 左右钩爪伸出，呈现钩住两只把手的动作。
3. 左右支撑电缸伸入侧缝附近。
4. 右手额外解锁电缸伸出，触发解锁。
5. 双手与抽屉同步向外移动，柜子平滑打开。
6. 关闭时双手重新到打开后的把手位置，柜子同步推回。
7. 电缸收回、双臂退让，下一次可以重复操作。
8. 三个场景有完整、清楚、合理的颜色。

界面只显示正常业务信息，例如“正在就位”“正在解锁”“正在拉出”“已打开”。不用增加模式开关、提示水印或硬件相关说明。

完成依据是实际画面和业务状态一致：不能只把页面状态改为已打开而模型没动，也不能让抽屉自行飞出、双手停在原地。

## 2. 当前代码可直接复用的部分

- 统一入口 `run_all.sh`。
- Web → TaskManager → CabinetClient → ROS 2 Action 的任务链路。
- 场景目录、工具集选择、导航和现有材质。
- Gazebo 柜体插件的状态发布、抽屉关节和现有取消/租约管理。
- 已经可达的双臂工作位姿及现有 MoveIt/关节轨迹能力。
- `scripts/validate/validate_db1_drawer` 的 Web 循环与非目标控件检查。

此前审查已有静态合同通过、Gateway 74 项测试通过、控制相关 Python 29 项通过和投影 C++ 9 项通过的记录。这些是历史基线，后续修改仍应跑对应回归。

此前的 cap3 一次成功、右钩爪反复回缩、解锁约 118.5 mm 偏差等问题说明原路线受接触动力学及触点几何制约。本目标下，无需先解决这些物理实验才能完成观看流程。

## 3. 实现路线：预制轨迹 + 统一进度 + 逻辑联动

### 3.1 动作准备与播放分开

准备阶段计算少量关键位姿和连接轨迹；播放阶段读取已验证轨迹并平滑执行，避免每次接触阶段重新随机规划。

关键点：

- 收臂位置；
- 柜前工作位置；
- 工具伸出后的把手保持位置；
- 抽拉路径上的若干位置；
- 开位退出位置；
- 关闭时重新接近开位把手的位置。

优先从当前成功工作位姿获取有效关节种子，使用现有 MoveIt 求解连续姿态。轨迹留在 control 包的场景配置或专用数据目录，记录适用模型/工具集；模型变化时重算。

使用实际关节旋转呈现机械臂动作，保持连杆连接连续；不通过拆开手腕或伸长机械臂网格解决可达性。

### 3.2 一份动作进度驱动所有相关对象

抽拉阶段使用一个统一进度 `s∈[0,1]`：

```text
drawer_position = start_position + ease(s) * travel
left_arm         = left_joint_trajectory(s)
right_arm        = right_joint_trajectory(s)
tools            = tool_trajectory(s)
```

- `ease` 采用起止速度平滑的插值；优先复用现有轨迹插值。
- 左右臂、工具和抽屉使用同一段时间基准。
- 以仿真时间控制播放；暂停仿真时动作也暂停。无进度超时另外使用单调时钟。
- 路径准备时检查双手在各采样点与把手的相对位置，避免中间段手柜分离。
- 完成时验证实际关节和抽屉位置已到终点，再发布成功。

### 3.3 Gazebo 内用运动学播放

为 db1 使用运动学驱动即可，允许通过 Gazebo 插件控制关节位置。无需依赖两个钩爪真实咬住把手产生拉力。

优先采用项目现有插件接口；若补充播放逻辑，保持为一个小型 C++ 模块。控制节点通过 ROS 2 topic/service/action 发命令，在 Gazebo 更新回调中更新模型并沿用状态发布。

**同一关节必须只有一个写入者：**

- 可以沿用现有稳定的位置控制器播放机械臂轨迹。
- 对仍受 effort/碰撞影响而抖动的工具，改为该动作期间的运动学驱动。
- 若需要移交控制权，在动作进入/退出边界处理一次；不在钩取阶段循环重启控制器。
- 播放时停用相冲突的抽屉弹簧、接触力或其他控制输出；停止/退出时恢复一致的保持目标。
- 关节状态、TF、Web 状态都应反映实际显示的位置。
- 控制权恢复前把接收控制器的目标对齐当前关节状态，避免动画结束瞬间跳回旧目标。

导航、地面及无关物体的碰撞保持原有行为。仅对造成这段动画抖动的工具内部/工具与柜体接触做局部处理，避免全局禁用碰撞导致机器人下沉。

### 3.4 各接触动作按逻辑联动

| 动作 | 完成条件 |
| --- | --- |
| 钩住把手 | 双手处于准备好的把手位置，钩爪完成伸出动画 |
| 支撑侧缝 | 左右支撑杆完成各自伸出动画 |
| 解锁 | 右手额外电缸完成伸出动画，当前动作处于解锁阶段 |
| 抽拉 | 左右臂和抽屉按统一进度同步移动 |
| 关闭 | 抽屉回到闭位，双手完成推回动作 |
| 收尾 | 电缸回收，双臂退出并停稳 |

右解锁杆与钩爪存在约 115 mm 的横向间距，当前点定义不能同时精确触达同一按钮位置。这里将额外电缸与右把手解锁建立逻辑联动即可；不继续调 8 mm 接触门限，也不改变按钮外观来追随杆端。

侧缝支撑同样以清楚的伸缩和合理的视觉位置为目标。无需持续计算真实反力或增加受力传感器。

## 4. 删除本路线上的旧阻塞门

db1 的可视化动作不再以以下条件启动或完成：

- hook effort 必须达到压贴力地板；
- cap2/cap3 的座封、接触保持与漂移试验必须先连续通过；
- finger3 物理触点必须进入 8 mm 解锁球；
- 固定闭位的 `drawer_position < 0.0025` 才允许开位重新钩取；
- 支撑杆必须建立真实受力接触；
- 必须靠碰撞耦合带动抽屉；
- 动作过程中必须反复自对中或重新寻找接触。

保留旧实现供参考，不大面积删除。将 db1 调度到新的可视化执行路径，避免新旧状态机同时控制同一动作。

既有 TaskManager/CabinetClient 若强制要求物理接触证据，应为这条执行路径更新终态映射：按播放实际完成、终态位置、工具回收及取消结果判定。不要为了绕过旧网关把未测量的接触力写成已确认。

不要求维护两套面向用户的模式。内部选择执行后端即可，界面保持普通打开/关闭操作。

## 5. 分阶段落地顺序

### P0：先恢复入口和确定工作轨迹

1. 核对最新代码与已有改动，保存本轮基线。
2. 用 `./run_all.sh --web` 启动。
3. 若 Nav2 再报 spin Action 未就绪，先核查发现/命名空间/启动时序，使用有界恢复；不要无限重启。
4. 为 db1 准备从收臂到工作位姿的确定轨迹，单独播放并检查画面。
5. 使用当前模型计算完整抽拉轨迹。先检查 0.30 m 行程的可达性和明显自穿插，再投入后续动画。

验收：入口可用、双臂能流畅到柜前，抽拉路径已有可播放数据。

### P1：先完成“手和柜子一起走”

先暂时略过支撑/解锁的细节动画，打通：工作位姿 → 同步拉出 → 同步推回 → 退出。

验收：

- 双手始终跟随把手；
- 柜子沿轨道移动；
- 底盘停在柜前；
- 无明显跳变、抖动或穿过柜体；
- 正反向均能完成。

这一步直接验证最重要的观看效果；通过后才增加电缸时序。

### P2：补齐电缸与状态时序

按“钩爪 → 支撑 → 解锁 → 抽拉”的次序加入动作。每个动作设置独立可调时长，让用户看得清楚；初始可采用 0.5～1 秒的电缸伸缩、数秒的抽拉，最终按画面效果调节。

关闭从当前实际开位开始：接近 → 钩住 → 支撑伸出 → 推回 → 收杆 → 退臂。若既有机构表现需要解锁杆收回或保持，由 Agent 按连贯画面自行确定，不引入额外交互。

验收：动作顺序清楚，状态文案与画面同步，没有工具跳变。

### P3：接入 Web、取消和重复运行

- 复用打开/关闭入口，保留任务 ID、忙状态和进度。
- 重复提交时按现有任务互斥处理，避免两段动画争用模型。
- 取消时所有关联对象在同一进度停止并保持；后续关闭从当前位置继续。
- 正常打开结束后保持打开，不立即自动推回；用户点击关闭再执行关闭。
- 关闭成功后可再次打开。
- 场景切换时停止当前播放并清理旧回调，避免新场景被旧任务驱动。

验收：Web 连续三个完整开合循环，以及中途取消后关闭恢复一次。

### P4：配色与观看体验

分别检查：

- `cabinet_operation`
- `electrical_mezzanine`
- `generator_plant`

补齐缺失材质、必要设备颜色和指示灯颜色；保持模型外形。检查正常视角下双臂、电缸和抽屉动作可见，必要时优化现有相机取景及照明。

验收：三个场景各保存一张全景，db1 保存一段完整开合录像。

## 7. 构建和验证

1. 每次按修改范围构建相关包；接口修改要重建对应消费者。
2. 检查轨迹有限数、关节限位、插值端点、打开/关闭方向和中途取消连续性。
3. 对控制权交接写必要测试：开始无跳变、结束不回旧目标、取消后无旧写入者。
4. 运行相关 Web 任务回归，确认普通 success/canceled/failed 状态语义正确。
5. 通过统一入口播放；截图/录像检查是本任务的核心验收，不以 pytest 全绿代替观看验证。
6. 跑三个开合循环和一次中途取消恢复；检查其他控件状态不变。
7. 用 `git diff --check` 检查提交差异。

如果 0.30 m 全行程在保留模型外形下确实无法得到合理手臂轨迹，Agent 自行调整停靠姿态、关节种子和路径。仍不可达时先交付可观看的最大连续行程，明确记录实际范围；不要在报告中把部分行程算作完整实现。
