# 电气夹层抽拉柜双手操作与全场景配色实施执行方案

> 文档状态：待执行，作为后续实现与验收基线  
> 编制日期：2026-09-01  
> 项目目录：`/home/live/work01`

## 1. 结论

用户描述和截图对应的场景是 `electrical_mezzanine`（电气夹层），不是
`generator_plant`（发电机场景）。

目标对象是电气夹层中的 5 组抽拉柜：

- `ds1`
- `ds2`
- `db1`
- `ds3`
- `dm1`

柜面上的小圆点只作为指示灯显示，不是供机器人按压的按钮，也不能作为 Web
或 ROS 2 中的可操作控件。

目标动作必须实现以下真实流程：

1. 右手三电缸进入右把手附近的解锁推进区并完成解锁推进。
2. 左右末端的支撑部件顶住柜面。
3. 右侧三电缸爪抓住右把手，左侧两电缸爪抓住左把手。
4. 两臂同步向外运动，将抽屉拉出。
5. 关闭时，两臂重新抓住左右把手并同步向内推进。
6. Web、任务层、ROS 2、MoveIt 和 Gazebo 必须形成真实闭环，不能只改界面或直接写入抽屉状态。

## 2. 实施范围

### 2.1 本次需要完成

- 将电气夹层的 5 组对象从“单手按压的 push-push 滑门”改为“双手抽拉柜”。
- 建立右手解锁推进区、左右把手抓取点和左右支撑点。
- 实现双臂同步拉出和同步推回。
- 实现 Gazebo 中的导轨、锁止、双侧抓取和状态反馈。
- 在 Web 中显示“抽屉柜”“打开”“关闭”等正确语义。
- 给以下 3 个内置场景增加统一、可辨识的颜色：
  - `cabinet_operation`
  - `electrical_mezzanine`
  - `generator_plant`

### 2.2 明确不做

- 不重新制作或替换 STL 网格。
- 不擅自改变模型尺寸、布局和可见外形。
- 不把指示灯改成按钮。
- 不直接修改 `build/`、`install/`、`log/`、`docs/build/` 中的生成文件。
- 不通过隐藏状态写入或假动作冒充物理执行成功。
- 不为本需求引入不必要的第三方依赖。

配色只修改 Xacro/SDF 中的 `visual material`，不改变碰撞体、惯量、关节和物理参数。

## 3. 当前模型识别结果

| 项目 | 当前对象 | 工程含义 |
|---|---|---|
| 场景 | `electrical_mezzanine` | 后续操作绑定电气夹层场景实例 |
| 抽屉根关节 | `ds1`、`ds2`、`db1`、`ds3`、`dm1` | 5 个 `prismatic` 关节是实际抽拉对象 |
| 抽屉主体 | `s1`、`s2`、`b1`、`s3`、`m1` | 面板及左右把手位于主体 STL 中 |
| 圆形机构 | `s1r`、`s2r`、`b1r`、`s3r`、`m1r` | 本需求未要求机器人旋转，暂不纳入动作 |
| 指示灯 | `s1p`、`s2p`、`b1p`、`s3p`、`m1p` | 只显示，不生成可操作控件 |

当前实现存在以下冲突：

- 5 组对象在 `electrical_mezzanine_controls.yaml` 中被声明为 `slider`。
- 当前采用单手向 `+X` 按压的 push-push 锁止逻辑。
- 当前主要使用右臂三电缸操作，没有双手抓取合同。
- 当前 `CabinetControl.msg` 只有 `BUTTON`、`KNOB`、`SWITCH`、`DOOR`、`SLIDER`，没有 `DRAWER` 类型。
- 当前 Gazebo 抓取服务只描述一个机器人链接，无法证明左右两个把手都已抓住。
- `ds1` 当前因高度约 `2.06 m` 超出已有单臂可达窗口，只展示状态，尚不能物理执行。

因此，本功能不能通过修改名称或状态标签完成，必须增加抽屉类型、双手状态机和双侧物理证据。

## 4. 目标操作流程

### 4.1 打开抽屉

1. **场景和工具检查**
   - 当前活动场景必须是 `electrical_mezzanine`。
   - 当前末端必须是工具套装 A。
   - 场景实例代次、控制目录和机器人状态必须一致。

2. **导航与停靠**
   - 根据目标抽屉选择独立导航工位。
   - 校验底盘位置、朝向、机械臂可达性和碰撞余量。

3. **右手解锁推进**
   - 右臂三电缸进入右把手附近的解锁推进区。
   - 按限定深度和速度推进。
   - 收到锁止解除证据后才能继续。
   - 解锁区不得绑定 `*p` 指示灯。

4. **双手支撑**
   - 左右末端的支撑面先贴住柜面。
   - 支撑接触用于抑制抽拉初始冲击和末端晃动。

5. **双爪抓取**
   - 右侧三电缸抓住右把手。
   - 左侧两电缸抓住左把手。
   - Gazebo 必须同时确认左右抓取点处于容差范围。
   - 任一侧未抓住时禁止抽拉。

6. **同步抽出**
   - 左右臂使用同一时间基准同步运动。
   - 抽屉沿柜面外法线运动。
   - 禁止顺序执行“先拉一边、再拉另一边”。

7. **开位确认**
   - 抽屉到达 `open` 位置。
   - 关节速度进入稳定范围。
   - 双臂同步误差、抓取状态和稳定时间均通过检查。

### 4.2 关闭抽屉

1. 如果双手已经释放，重新到达开位抽屉的左右把手。
2. 建立双手支撑和双侧抓取证据。
3. 左右臂同步向柜体内部推进。
4. 抽屉回到 `closed` 位置并恢复锁止。
5. 先松开两侧爪子，再撤离支撑面。
6. 双臂回到安全运输位。

关闭过程不按压指示灯，也不重复打开阶段的解锁推进。

## 5. 抽屉状态机

| 状态 | 进入条件 | 允许动作 | 异常处理 |
|---|---|---|---|
| `CLOSED` | 抽屉在关位且稳定 | 开始打开流程 | 状态不可信时禁止动作 |
| `UNLOCKING` | 右手到达解锁区 | 限深推进 | 超力或超时立即撤回 |
| `READY_TO_GRASP` | 解锁证据成立 | 双手接近和支撑 | 解锁证据丢失则回退 |
| `BIMANUAL_GRASPED` | 左右把手均抓取 | 同步抽出或推回 | 任一侧脱离立即制动 |
| `OPENING` | 同步抽出已启动 | 继续到开位 | 偏载、碰撞或停滞则中止 |
| `OPEN` | 开位稳定 | 保持、关闭或释放 | 位置漂移超限进入故障 |
| `CLOSING` | 双侧抓取且收到关闭请求 | 同步推回 | 偏载、碰撞或停滞则中止 |
| `ABORTED` | 任一安全门触发 | 制动、释放、撤离 | 保留失败证据和明确原因 |

## 6. 跨层技术方案

### 6.1 ROS 2 接口

1. 在 `xczs_inspection_robot_interfaces/msg/CabinetControl.msg` 中增加：

   ```text
   uint8 TYPE_DRAWER=5
   ```

2. 继续复用 `OperateCabinetControl.action` 的 `SET_STATE` 和 `SET_POSITION`，避免重新建立一套业务 Action。

3. 增加双手抓取服务，至少包含：
   - `control_id`
   - 左右机器人链接名称
   - 左右把手局部坐标
   - `attach` / `detach`
   - 左右抓取是否成立
   - 失败原因和物理证据

4. 新服务放入 `xczs_inspection_robot_interfaces/srv/`。

### 6.2 场景控制合同

修改：

- `xczs_inspection_robot_control/config/scene_controls/electrical_mezzanine_controls.yaml`
- `xczs_inspection_robot_control/config/scene_controls/electrical_mezzanine_adapter.yaml`
- `xczs_inspection_robot_control/config/scene_controls/electrical_mezzanine_scene.yaml`

每组抽屉需要独立配置：

```yaml
type: drawer
joint_name: ds1
state_ids: [closed, open]
state_positions: [0.0, 0.30]
outward_axis: [-1.0, 0.0, 0.0]
unlock_zone: [...]
left_handle_point: [...]
right_handle_point: [...]
left_support_point: [...]
right_support_point: [...]
navigation_station: {...}
required_toolset: A
```

说明：

- `0.30 m` 是根据原模型行程提出的初始值，最终值必须通过碰撞余量和 Gazebo 实测确认。
- 当前坐标推断柜面外拉方向为 `-X`，写入 5 个关节前必须先用小位移验证方向。
- 不能照搬旧 push-push 的 `slider_release_position`、`slider_open_press_offset` 等参数。
- `*p` 指示灯不能进入 `operable_control_ids`。

### 6.3 Gazebo 模型和物理插件

1. 继续复用 `ds1`、`ds2`、`db1`、`ds3`、`dm1` 五个根部导轨关节。
2. 将锁止逻辑改为：
   - 未解锁时禁止向外拉。
   - 右手完成解锁推进后允许抽拉。
   - 关闭到位后恢复锁止。
3. 为右把手附近建立不可见的逻辑接触区，不新增可见按钮。
4. 双手抓取必须同时建立。
5. 单侧抓取请求必须被插件拒绝。
6. 执行期间持续检查左右抓取点误差和抽屉非导轨方向偏移。
7. `Reset`、任务取消和场景切换必须无条件释放两侧约束。

双刚性约束可能形成闭环并导致 Gazebo 抖动。实现时优先评估：

- 一侧主约束，负责传递抽拉运动。
- 另一侧柔顺约束或受监控接触，负责证明双手同时操作并限制偏载。
- 通过扰动测试确定最终刚度、阻尼和容差。

### 6.4 C++ 双臂控制

功能节点继续放在 `xczs_inspection_robot_control`，优先使用 C++。

实现要求：

- 复用现有导航、操作租约、工具套装检查和 Action 结果基础设施。
- 抽屉分支单独实现双臂状态机。
- 左右臂可以分别规划到预抓取位。
- 抽拉和推回段必须合并到统一时间轴并同时执行。
- 三电缸和两电缸的伸缩量从逐抽屉配置读取，不能硬编码为全局常量。
- 持续输出解锁、支撑、左右抓取、同步误差、抽屉位置和失败原因。
- 工具套装错误、场景代次变化、双手未就位或目标不可达时，在改变抽屉状态前失败。

### 6.5 Web 和任务层

- 控件类型显示为“抽屉柜”。
- 可用动作显示为“打开”和“关闭”。
- 不再显示“按钮”“按压”或 push-push 滑门语义。
- 任务请求继续通过当前 ROS 2 Action 网关。
- SSE 和任务详情显示以下阶段：
  - 解锁
  - 支撑
  - 双侧抓取
  - 抽出
  - 开位到达
  - 推回
  - 关位到达
  - 释放
- 场景切换或 `catalog_generation` 改变时立即取消旧操作。

## 7. 三个内置场景配色

### 7.1 统一颜色语义

| 视觉对象 | 建议色系 | 目的 |
|---|---|---|
| 环境主体 | 低饱和蓝灰、暖灰 | 建立空间层次，避免全灰 |
| 抽屉和柜门 | 中性浅蓝灰 | 从背景中区分可操作面板 |
| 把手和机构 | 深灰金属色 | 突出轮廓，但不伪装成按钮 |
| 指示灯 | 红、绿、琥珀 | 表示灯光，不产生可操作语义 |
| 安全构件 | 黄色、橙色 | 表示警示和危险边界 |

### 7.2 场景落点

#### `cabinet_operation`

- 统一柜体主体颜色。
- 按钮、旋钮、摇杆、把手使用不同的类型色。
- 不改变现有控制柜结构和物理参数。

#### `electrical_mezzanine`

- 抽屉面板使用浅蓝灰。
- 左右把手和圆形机构使用深灰金属色。
- `*p` 指示灯使用红、绿或琥珀色。
- 指示灯即使高亮，也不能在 Web 中出现按压动作。

#### `generator_plant`

- 地面、墙面和大型设备使用不同明度的工业灰或蓝灰。
- 小型灯件使用指示色。
- 不把该场景的小型灯件登记为本次抽屉目标。

| 最终入口 | `./run_all.sh` 启动后的完整 Web/Gazebo 闭环通过 |

建议将双臂同步启动差的首轮验收值设为不大于 `100 ms`；完成真实仿真测试后再根据控制器周期调整。

## 11. 风险和停止条件

### 11.1 右把手解锁区没有独立网格

现有模型中，右把手附近的解锁部件可能已经合并在抽屉主体 STL 中，而 `*p` 已被用户明确为指示灯。

处理：

- 使用不可见逻辑接触区实现解锁检测。
- 先提供位置截图或 Gazebo 标记确认。
- 不擅自新增可见按钮。

### 11.2 双侧刚性约束可能抖动

处理：

- 评估“一侧主约束 + 一侧柔顺约束”。
- 执行静止、抽拉、急停和外力扰动测试。
- 依据实测调整刚度和阻尼。

### 11.3 `ds1` 高度不可达

当前已有记录表明 `ds1` 约 `2.06 m`，超出原单臂操作窗口。

处理：

- 重新设计双臂专用停靠位和底盘姿态。
- 尝试不同朝向和手臂分工。
- 如果现有机器人几何仍不可达，必须停止并提交可达性证据及可选方案，不能伪造成功。

### 11.4 抽拉方向需要实测

旧模型使用 `+X` 做按压，新的抽拉目标预期向 `-X` 外拉。

处理：

- 先在单个抽屉上做受控小位移。
- 确认外法线后再批量修改其余 4 组。

### 11.5 生成文件污染

IDE 当前打开的 `docs/build/...` 文件属于生成产物，不能在其中修复接口代码。

处理：

- 只修改源码包。
- 使用干净构建重新生成 Python 接口。
- 不提交 `build/`、`install/`、`log/` 和 `docs/build/`。

### 11.6 必须暂停并请求确认的情况

发生以下任一情况时暂停实施：

- 必须增加或改变可见柜体机构。
- 必须改变模型尺寸或外形。
- 必须引入新的第三方依赖。
- 实测证明 `ds1` 在现有机器人几何下不可达。
- 用户描述的右手解锁推进区无法从现有模型中唯一确定。
